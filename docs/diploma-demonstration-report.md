# Звіт про перевірку та демонстрацію DevSecOps CLI Kit

Дата підготовки: 6 листопада 2026 року.
Поточна версія вихідного коду: `0.16.0.dev0`, неопублікована.
**Стан: локальна підготовка; хмарне приймання ще не проводилось.**

Це окремий звіт для дипломного проєкту. Він поступово доповнюється
реальними результатами, скріншотами та коментарем до кожного кадру.
Наявність плану кадру не означає, що перевірка вже пройшла.

## Умови демонстрації

| Питання | Зафіксоване рішення |
| --- | --- |
| Репозиторій | Використовувати поточний `tidyOpposite/devsecops-pipeline-kit-aws-lambda`. Другий репозиторій необов'язковий. Push, налаштування GitHub і запуск Actions ще не виконувались. |
| Люди | Один оператор. Іншої довіреної людини для approval немає. Незалежне production-схвалення не можна вважати перевіреним. |
| AWS | Один Free акаунт; заявлений власником залишок кредитів — $100. Тип плану, дата завершення кредитів і доступні права ще не перевірені. |
| Workload | [Text Stats](../examples/text-stats/README.md): невелика stateless Lambda для аналізу тексту, без БД і зовнішніх API. |
| Робоче середовище | macOS локально; Ubuntu — через CI після синхронізації коду. Windows і WSL2 не перевірені та вилучені із заявленої підтримки поточного релізу. |
| Час деплою | Лише після завершення локальних виправлень. Підготовка прикладу не запускає AWS. |

Окремий репозиторій зручний для незалежного розвитку application code, але
для цієї демонстрації не потрібен. Образ прикладу будується окремо;
production workflow kit, як і раніше, споживає готовий ECR image за digest.

### Межі приймання за цих умов

Поточний `prod` вимагає незалежного reviewer, забороняє самосхвалення та
обхід адміністратором. GitHub також прямо зазначає: при забороні self-review
ініціатор не може сам схвалити свій deployment.
Джерело: [GitHub deployment protection rules](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

Окремий `cloud-acceptance` тест вимагає sandbox AWS account, відмінного від
production. Другий workspace або префікс в одному акаунті не доводить
ізоляцію між акаунтами.

Тому **одноосібний сценарій у тестових ресурсах одного акаунта ще потрібно
реалізувати та перевірити окремо**. Не вимикати наявний `prod` gate й не
використовувати другий власний GitHub-акаунт як удаваного незалежного reviewer.
Це відкрите питання підготовки; поки воно не закрите, повний AWS/GitHub
production acceptance залишається непідтвердженим. У дипломі можна
окремо показати справну роботу тестового середовища й коректне блокування
production-деплою без потрібного схвалення.

### Що підготувати власнику перед хмарним етапом

1. Можливість увійти до AWS Console та пройти MFA. Налаштування локального
   доступу виконувати на своєму комп'ютері; ключі й токени не надсилати в чат.
2. AWS account ID та один обраний регіон. Всі ресурси демонстрації створювати
   лише в цьому акаунті/регіоні з окремими іменами та тегами проєкту.
3. На сторінці Billing/Free Tier перевірити фактичний Free/Paid plan, залишок
   і дату завершення кредитів. Наявність $100 не є кошторисом або гарантією
   безкоштовності всіх ресурсів. До створення ресурсів узгодити кошторис,
   обмеження витрат і час роботи демонстрації.
4. Знати орієнтовну дату захисту: ресурси можна залишити до повторної
   демонстрації або прибрати після збору доказів.

AWS описує строк Free plan/кредитів та обмеження сервісів у
[Free Tier FAQ](https://aws.amazon.com/free/free-tier-faqs/). Конкретний план
цього акаунта не можна визначити лише за залишком коштів. Перехід на Paid
plan не виконується в межах цієї підготовки.

Створювати другий акаунт/репозиторій, шукати reviewer або писати Lambda
самостійно власнику для локальної підготовки не потрібно. Коли реалізація
одноосібного хмарного шляху буде готова, його перевірка матиме власний
перелік ресурсів і результатів та не підмінятиме production acceptance.

Інструмент керування комп'ютером відмовив у доступі до Terminal. Тому

команд і unit tests не перетворюється на намальовані «скріншоти».
Для AWS потрібні справжні сторінки вже створених ресурсів; зараз такі
кадри не підготовлені.

Оригінали кадрів і transcripts зберігати локально, наприклад у
`dist/devsecops/diploma-evidence/` (ігнорується Git), та у незалежній копії.
Перед додаванням до публічного звіту приховати credentials, authorization
headers, пошту та зайві дані акаунта. У звіті розміщувати тільки перевірені
кадри; приватні оригінали не комітити.

## Що означає «можна видалити після»

Йдеться про **створені хмарні ресурси**, а не про диплом чи звіт.
Lambda, API Gateway, ECR images, S3, logs, state backend і KMS мають
різну вартість та залежності. До видалення потрібно зберегти докази,
необхідні дані та зрозуміти, чи знадобиться повторний показ.

Зараз видалення нічого не дозволено й не запускається. Перед завершенням
хмарної демонстрації окремо зафіксувати вибір «залишити до захисту» або
«прибрати тестові ресурси після збереження доказів» та точний перелік.
Використовувати [runbook завершення демо](runbooks/finish-demo.md), зберегти
звіт/кадри поза видаленими ресурсами й перевірити витрати пізніше.
Спільні або сторонні ресурси акаунта не включати до очищення.
