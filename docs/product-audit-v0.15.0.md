# Аудит готовності DevSecOps Pipeline Kit v0.15.0

Перевірено `main` на коміті `438902e` 4 листопада 2026 року. Обсяг аудиту охоплює встановлення, CLI та інтерактивне меню, конфігурацію, Terraform, GitHub Actions, AWS, сканування, деплой, відкат і докази для релізу.

**Вердикт.** Локальний демосценарій працює. До приймання як робочого продукту потрібно закрити P0, пройти повний сценарій у контрольованому AWS-акаунті та повторити перевірку P1. P0 блокує безпечний деплой або приймання релізу. P1 має бути виправлено для заявлених робочих сценаріїв. P2 знижує зручність і керованість продукту.

## P0 · Блокери приймання

1. **AWS відхилить конфігурацію Lambda.** Terraform задає `AWS_REGION` у `environment.variables`, хоча Lambda резервує цю назву. `terraform validate` проходить, бо він перевіряє структуру конфігурації. **Закриття.** Видалити це присвоєння та підтвердити створення Lambda з чистого AWS-оточення. [Модуль Lambda](../terraform/modules/lambda/main.tf#L112), [правила AWS](https://docs.aws.amazon.com/lambda/latest/dg/configuration-envvars.html#configuration-envvars-runtime).
2. **Документований OIDC trust несумісний із job деплою.** Зразок IAM очікує `repo:OWNER/REPO:ref:refs/heads/main`. Job оголошує `environment: prod`, тому за стандартним форматом GitHub надсилає `repo:OWNER/REPO:environment:prod`. Інструкція також не дає повної пари перевірених trust policies для PR-плану та ручного плану. **Закриття.** Поставити робочі приклади для обох ролей, обмежити `prod` гілкою `main` на GitHub і перевірити, що дозволені job отримують саме свої ролі. [IAM-інструкція](../AWS_policy.md#L55), [job деплою](../.github/workflows/deploy.yml#L206), [формат OIDC subject](https://docs.github.com/en/actions/reference/security/oidc#example-subject-claims).
3. **Шлях через GitHub UI обходить частину production-політики CLI.** `deploy prod` блокує вимкнений `/health`, а обробник конфігурації в Actions відхиляє `FAIL` і окремо перевіряє прапорець approval, але приймає `WARN` про вимкнений `/health`. Сам job тоді пропускає smoke test. Наявність прапорця в JSON не доводить, що в GitHub налаштовано reviewers. **Закриття.** Застосувати єдиний production policy в runner для CLI та `workflow_dispatch`. Перевірити reviewer, обмеження гілки, самосхвалення та обхід правил для цільового `prod`. [Політика CLI](../cli/devsecops_cli/main.py#L2815), [runner](../cli/devsecops_cli/workflow.py#L46), [smoke test](../.github/workflows/deploy.yml#L358).
4. **Підписаний `health` передає заголовки AWS іншому endpoint.** Команда приймає `http://` та довільний host, а `urlopen` пересилає `Authorization` і `X-Amz-Security-Token` під час редиректу. Відтворено на двох локальних HTTP endpoint із вигаданим токеном. **Закриття.** Вимагати HTTPS і очікуваний API Gateway host або явно дозволений custom domain. Блокувати редиректи в підписаному режимі та перевірити, що другий endpoint не отримує заголовки. [HTTP-клієнт](../cli/devsecops_cli/aws.py#L490).
5. **Відкат не гарантує повернення останньої робочої версії.** Початковий workflow зчитував `Code.ImageUri`, приховував помилки читання й продовжував apply. Recovery повторно застосовував весь stack без перевірки `/health` після відновлення. ECR міг видалити активний або попередній `sha-` образ після виходу за ліміт 30. **Закриття.** Фіксувати `Code.ResolvedImageUri` до будь-якої зміни, відрізняти перший деплой від помилки доступу, утримувати recovery digest і перевіряти функцію після відновлення. Підтвердити відкат після навмисно зламаного `/health` та узгодженість Terraform state. [Зняття recovery point](../.github/workflows/deploy.yml#L273), [відновлення](../cli/devsecops_cli/recovery.py#L98), [ECR](../terraform/modules/ecr/main.tf#L1), [поля AWS Lambda](https://docs.aws.amazon.com/cli/latest/reference/lambda/get-function.html#output).
6. **Намір деплою не фіксує digest образу й версію конфігурації.** Допустимий тег може бути змінним у зовнішньому ECR. CLI і runner перевіряють назву тегу, а план, підтвердження та apply не мають спільного digest конфігурації й образу. Зміна repository variables між локальною перевіркою та постановкою run у чергу може змінити backend, регіон або параметри stack. **Закриття.** Визначати digest перед погодженням, фіксувати revision конфігурації та commit і перевіряти їх у runner. Відхиляти розбіжності з перевіреною конфігурацією. [Перевірка образу](../cli/devsecops_cli/images.py#L25), [dispatch](../cli/devsecops_cli/deploy.py#L170), [джерело конфігурації job](../.github/workflows/deploy.yml#L46).
7. **`criteria --strict` приймає фіктивні докази.** У тимчасовому каталозі створено всі обов’язкові JSON із `{}`, а текстові файли зі словом `placeholder`. CLI повернув `stable_ready=true`. Workflow публікації запускається за тегом і цього gate взагалі не викликає. **Закриття.** Перевіряти зміст, `conclusion=success`, виконання deploy job, SHA релізу, перевірений digest, докази відновлення та сумісності. Публікація стабільного тегу має падати на підставних, невідповідних і відсутніх доказах. [Перевірка evidence](../cli/devsecops_cli/main.py#L2096), [workflow релізу](../.github/workflows/release.yml#L3).
8. **Робочий AWS/GitHub сценарій досі без підтвердження.** У перевіреному upstream-репозиторії API повернув `main.protected=false`, для `prod` — HTTP 404, списки repository variables/secrets порожні. У видимій історії немає `workflow_dispatch`. Перевірений PR-run завершився помилкою на `Require separate AWS plan role`. Це спостереження про upstream, а конфігурацію окремого deployment repository ще треба перевірити. **Закриття.** У цільовому репозиторії під’єднати окремі OIDC ролі, захист `main` і `prod`. Зберегти докази успішного першого деплою, оновлення, невдалого health gate та реального відновлення. [PR-run](https://github.com/tidyOpposite/devsecops-pipeline-kit-aws-lambda/actions/runs/33792383423), [production evidence](production-deployment-evidence.md).

## P1 · Логіка та експлуатація

9. **Готовність до першого деплою змішана зі станом уже розгорнутого продукту.** Runbook вимагає `status --strict` до dispatch. Без `--deep` перевірка не має cloud evidence, а з `--deep` відсутні Lambda, API Gateway та логи вважаються прогалинами навіть перед першим створенням. `next_action` водночас може радити deploy через ту саму відсутність ресурсів. **Закриття.** Виділити три стани — `Ready to deploy`, `Deployed and healthy`, `Release evidence complete`. Перевірити окремий preflight для порожнього AWS-оточення. [Gate](../cli/devsecops_cli/readiness.py#L390), [підказка](../cli/devsecops_cli/context.py#L312), [runbook](production-deployment-evidence.md#L89).
10. **Перевірка образу перед dispatch переважно синтаксична.** Коректно сформований, але неіснуючий digest або образ з неправильною архітектурою може пройти CLI preflight. Runner може змінити KMS/ECR перед тим, як виявить непридатний образ. Terraform фіксує `x86_64`. Додатково AWS doctor для BYO ECR не передає `--registry-id`, тож cross-account lookup іде в реєстр поточного акаунта. **Закриття.** У runner до змін перевірити digest, фактичний registry ID, регіон, формат, архітектуру та доступ. Додати окремий відтворюваний крок створення ECR для сценарію з вбудованим реєстром. [CLI preflight](../cli/devsecops_cli/main.py#L2889), [ECR lookup](../cli/devsecops_cli/aws.py#L337), [архітектура Lambda](../terraform/modules/lambda/main.tf#L98), [вимоги Lambda до образів](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html#images-reqs).
11. **GitHub run і журнал можуть розійтися.** Якщо dispatch не повернув URL, CLI бере перший новий run із тією самою назвою. Два паралельні запити можуть прив’язати локальний запис до чужого run, а звичайна concurrency-група може скасувати попередній pending run. Без знайденого ID `--watch` може завершитися з кодом `0`, так і не дочекавшись результату. Відкат за замовчуванням довіряє останньому локальному запису без перевірки його висновку. **Закриття.** Корелювати за точним run ID або унікальним ID запиту. Прив’язати recovery digest до виконаного run і показувати явний стан `dispatched, run unconfirmed`. [Кореляція](../cli/devsecops_cli/deploy.py#L284), [watch](../cli/devsecops_cli/main.py#L3185), [GitHub concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
12. **`deploy status` може позначити пропущений deploy як успіх.** Перевірка явного `--run-id` обмежується workflow, подією і гілкою. Вона може прийняти ручний `plan` або запуск із пропущеним production job. Exit code вважає `skipped` і `neutral` успішними. У GitHub UI користувач може вибрати `deploy` для `dev`/`staging`, хоча відповідний job запускається тільки для `prod`. **Закриття.** Перевіряти вид операції й результат саме deploy job, а непідтримувані комбінації відхиляти з поясненням. [Вибір run](../cli/devsecops_cli/main.py#L3037), [exit code](../cli/devsecops_cli/deploy.py#L387), [dispatch inputs](../.github/workflows/deploy.yml#L12).
13. **Валідні для CLI параметри можуть бути невалідними для AWS.** Відтворено `OK` для `log_retention_days=2` та 32-символьного `project_name`. CloudWatch приймає фіксований список значень, а така назва утворює workload bucket на 64 символи в `prod` і 67 у `staging`, при ліміті 63. **Закриття.** Узгодити CLI, схему й Terraform з межами AWS. Для вже створених bucket зберегти їхні фізичні імена. [CLI validation](../cli/devsecops_cli/config.py#L930), [назви bucket](../terraform/modules/storage/main.tf#L1), [CloudWatch](https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_PutRetentionPolicy.html), [S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucketnamingrules.html).
14. **Ролі та секрети GitHub перевіряються поверхово, а запис частковий.** `github setup --apply` послідовно оновлює змінні та secrets, зупиняється на першій помилці та може лишити змішаний стан. Прямий шлях пропускає ненадані ролі, а doctor бачить лише назви repository secrets, тому не доводить, що ролі різні, доступні та правильно налаштовані. Environment secrets потребують окремої перевірки. **Закриття.** Явно показувати й фіксувати `owner/repo`, валідувати ARN до запису, показувати частковий результат та ідемпотентний retry. Перевірити OIDC окремими job для кожної ролі. [Запис](../cli/devsecops_cli/main.py#L755), [діагностика](../cli/devsecops_cli/github.py#L537).
15. **Smoke check та evidence runbook допускають хибний результат.** У workflow `curl --fail` сам по собі не вимагає 2xx, тому редирект може пройти перевірку. Runbook дістає `Code.ImageUri` з `get-function-configuration`, де цього поля немає. Команда Terraform `output` покладається на локально ініціалізований і вибраний workspace без явної перевірки `prod`. **Закриття.** Вимагати узгоджений 2xx і чіткий timeout. Фіксувати digest через `get-function`, а backend, workspace та акаунт — разом із доказами. [Workflow smoke check](../.github/workflows/deploy.yml#L358), [runbook](production-deployment-evidence.md#L241), [AWS CLI reference](https://docs.aws.amazon.com/cli/latest/reference/lambda/get-function-configuration.html#output).
16. **Роль для PR-плану довіряє коду PR із того самого репозиторію.** Job із `id-token: write` завантажує код PR та запускає Python і Terraform. Перевірка `head.repo == repository` відсікає forks, але дозволяє авторам внутрішніх гілок виконувати код з доступом до OIDC job і його AWS scope. Окремо незаповнений upstream закономірно дає червоні PR-плани. **Закриття.** Залишити credential-free перевірку для всіх PR, а AWS-backed plan дозволяти в явному довіреному контексті з ізольованим state. Розділити policy для шаблону й налаштованого deployment repo. [PR plan job](../.github/workflows/deploy.yml#L100).
17. **Оновлення інсталятора може зламати робочу копію.** Скрипт видаляє активний venv до створення нового, а launcher записує поверх наявного файла. Якщо створення venv чи встановлення залежностей впаде, старий CLI втрачено. **Закриття.** Підготувати нову версію окремо, перевірити `--version`, атомарно перемкнути launcher і протестувати невдале оновлення. [Інсталятор](../install.sh#L325).
18. **Відтворюваність security gates і CI неповна.** Snyk встановлюється як `npm install -g snyk` після отримання AWS credentials. CI перевіряє Terraform статично і не ловить AWS runtime constraints. Dependabot усе ще запускає pip для відсутнього `/lambda_function` та Docker для відсутнього Dockerfile. **Закриття.** Зафіксувати версію Snyk, звузити доступ сканера до необхідних прав, прибрати застарілі jobs та додати інтеграційний acceptance-сценарій в ізольованому оточенні. [Snyk](../.github/workflows/deploy.yml#L264), [CI](../.github/workflows/ci.yml#L70), [Dependabot](../.github/dependabot.yml#L8).

## P2 · CLI, UX та документація

19. **Перший запуск починається раніше, ніж користувач отримує файли проєкту.** README дає команду інсталяції, але не дає в Quick Start конкретних `clone` і `cd`. Wheel містить CLI, а setup потребує Terraform та workflow з checkout. `repo_root()` використовує поточну директорію, тому запуск навіть із піддиректорії видає повідомлення про відсутні файли. **Закриття.** Один копійований шлях від чистої системи до демо. Піддиректорії мають знаходити корінь або отримувати точну команду переходу. [Quick Start](../README.md#L60), [визначення кореня](../cli/devsecops_cli/main.py#L364).
20. **Демо виглядає як частково зламаний production setup.** Відтворено `Guided setup complete`, `Environment target: prod`, AWS/backend warnings і наступний `status`, який одразу показує `Production readiness: Blocked`. Команда для нового користувача в README вибирає standard/balanced, хоча локальний сценарій не має AWS. **Закриття.** Зробити demo стандартним шляхом без credentials, показати результат `Demo complete`, а перехід у production винести в окрему дію. [Quick Start](../README.md#L60), [summary](../cli/devsecops_cli/main.py#L1789).
21. **Зміна режиму може переписати налаштування без огляду змін.** `setup --mode production --yes` із demo-конфігурації застосовує `enterprise` до наявного файла. Snapshot є, але пресет змінює політики та per-environment параметри одразу. Валідація аргументів запускається вже після запису нового setup state. **Закриття.** Перед записом валідувати аргументи, показувати diff і вимагати явного вибору для заміни вже налаштованих параметрів. [Перехід режиму](../cli/devsecops_cli/main.py#L1846), [застосування пресету](../cli/devsecops_cli/main.py#L1887).
22. **Термінал показує елементи керування там, де вони не працюють.** `status` і `dry-run` друкують `[i] details` поза меню, а setup двічі друкує однаковий `Next command`. У тесті з `COLUMNS=55` рядки досягали 77 символів. `menu </dev/null` повертає `70`, а `health --url 'http://[broken'` описує помилку вводу як `Unexpected error`. **Закриття.** Розділити інтерактивне і звичайне виведення, адаптувати ширину, зробити одну копійовану команду та обробляти EOF і невалідний URL як очікувані випадки. [Рендер CLI](../cli/devsecops_cli/main.py#L418), [меню](../cli/devsecops_cli/main.py#L4683), [обробник URL](../cli/devsecops_cli/aws.py#L490).
23. **Статус релізу й інструкції суперечать одне одному.** README і metadata позначають продукт як alpha, а RC checklist та production walkthrough досі посилаються на `v0.14.0`, хоча `v0.15.0` опубліковано. `criteria` навіть перевіряє старі release notes як latest. Quick Start запускає installer з рухомого `main`, хоча реліз має власний installer і контрольні суми. **Закриття.** Синхронізувати версії, дати pinned install для дипломної демонстрації і оновлювати статус готовності після проходження acceptance. [README](../README.md#L1), [RC checklist](v1.0.0-release-candidate-checklist.md), [criteria](../cli/devsecops_cli/main.py#L2290), [реліз](https://github.com/tidyOpposite/devsecops-pipeline-kit-aws-lambda/releases/tag/v0.15.0).

## Що перевірено під час аудиту

- Ізольоване встановлення `v0.15.0` із GitHub Release, перевірка SHA-256 wheel та запуск установленого CLI. У чистому локальному checkout виконано `setup --mode demo --yes --strict`.
- Усі 183 тести пройшли на macOS arm64 і Python 3.14.7 після встановлення опційних Rich/Textual у тимчасове середовище. Terraform 1.16.0 пройшов `fmt -check -recursive` та `init -backend=false` + `validate` для основного stack і bootstrap.
- Зіставлено код, публічні релізні матеріали та доступні read-only дані GitHub. Відтворення проводилися у тимчасових каталогах. Робочий AWS apply, реальний rollback і WSL2 transcript залишаються відкритими. На машині аудиту відсутній AWS CLI.

## Порядок приймання

1. Завершити всі виправлення коду, UI та документації перед реальним деплоєм.
2. Перевірити UI і документацію на чистому macOS, Ubuntu та WSL2 в межах заявленої матриці. Зафіксувати команду, exit code і результат першого запуску, відновлення після помилки та оновлення.
3. У чистому deployment repo пройти встановлення, backend, OIDC plan і `status --pre-deploy --strict` до створення workload. Виконати підтверджений deploy образу A, успішний deploy B та deploy образу C з навмисно зламаним health. Звірити активний digest B, Terraform state та `/health`. Окремо виконати ручний rollback до A і перевірити ті самі показники.
4. Підготувати evidence bundle одного конкретного release commit. Звірити CI, хмарні run ID, образи та контрольні суми пакета. Стабільний реліз приймати після успішної змістової перевірки evidence.
